### How it works, in one paragraph

The assistant is one surface (`POST /api/assistant/ask` + drafting/task/suggestion/settings routes and the AI Assistant view) that parses a plain-language task into intents it can execute with the existing agents — draft captions via Agent 1, draft comment/message replies via Agents 3/4, create a task, analyse stored data, find recurring questions, create a content brief — and returns a concrete work product (drafts, suggestions, classifications, analysis, created tasks), saying plainly in the result what it did and what (if anything) it could not do. Brand voice, reply rules, and approved-template phrasing are per-tenant user-provided settings (`assistant_settings`); when none is set the assistant uses a neutral tone and says so, and when a needed fact is missing the draft carries a literal `[NEEDS INPUT: …]` placeholder instead of an invented figure. Out-of-scope intents (leads, ads, listening, reporting, WhatsApp, commerce) are refused with a clear "not in the MVP" message, never attempted; unknown intents are refused, never guessed. Sensitive intents (publish, send, delete, budget, manage asset) never execute: with an identified target the assistant prepares a pending approval under the existing four-eyes workflow (the human approves the exact text/action); without a target — and always for budget, which has no approval executor in the MVP — it refuses plainly (see §5, AC-5-04 note). Every suggestion records its outcome (approved as-is / edited / discarded) with the correction recorded when edited or discarded, and nothing is sent or published for a reviewed suggestion. A recurring question (same classification-intent label appearing at least `minCount` times, default 3, across the latest classification of each inbox message and each comment — a deterministic mock rule, labelled as such) becomes a content brief TASK for Agent 1, never an automatic publication. Runs are idempotent (same tenant + idempotency key replays the original result with `deduped: true`), agent work retries once then escalates to a human task, and every run, draft, task, approval, and review writes to the append-only audit log. All context is assembled tenant-scoped; every query is tenant-scoped from the session.

## 2. Stack chosen + why

Unchanged from Phases 1–4: Node.js 24, zero npm dependencies, `node:sqlite`, built-in `http`, `node:test`. Phase 5 adds these configuration decisions:

| Choice | Rationale |
|---|---|
| Mock AI provider interface for the assistant (same pattern as Agents 1, 3, 4) | Owner open question Q6 (AI provider/model) is undecided. The assistant runs on the deterministic mock provider, labelled `provider: 'mock'` in code, API responses and UI, and never calls a real AI API, never invents a provider/model, and never presents mock output as real AI output. |
| Recurring-question rule: same classification-intent label ≥ minCount (default 3) across latest classifications | The docs require a deterministic mock rule and forbid claiming real trend detection. The rule is recorded in code and in the evaluation output (`labelledMock: true`); the evaluation harness's own sample check used minCount=2. |
| Idempotency via a module-owned `assistant_runs` table (tenant + key UNIQUE, full result JSON) | The assistant must never execute twice on a retry. The table is created lazily by `src/agents/assistant.mjs` (`CREATE TABLE IF NOT EXISTS` on first run), not by `db.mjs` SCHEMA — a deliberate divergence, recorded in §7 (D-8). The Orchestrator dedupe key IS the assistant idempotency key, so a re-routed task returns the original result (second guard). |
| B-12: Agent 7 `reviewText` extended to inbox replies, advisory only | The shared `reviewText` core (R-01…R-05, Phase 0 docs only, no new rules) now runs in `request-send` before the approval is created. A `block` verdict does NOT refuse the approval request — the human approver decides. CLOSED, not left open (see §6). |
| Budget requests refused, not approval-queued | No budget executor exists in the MVP (Agent 6 is Phase 6+; the gate check confirms a pending `budget_change` approval cannot execute). Queuing a budget change for approval would promise an execution that cannot happen. The assistant refuses plainly and says a human must do it (see §5, AC-5-04 note). |
| No numeric evaluation pass mark | Thresholds are NEEDS CLARIFICATION (roadmap §15 item 5). The harness records raw rates/counts only; "ready" is the owner's decision at the MVP gate. No threshold was invented anywhere in code, tests, or records. |

## 7. Deliberate implementation decisions (divergences from the docs, all recorded)

1. **D-1 — the assistant prepares, never executes.** Any sensitive intent is either turned into a pending approval (publish/send/delete/manage_asset with an identified target) or refused (budget; no target). No assistant path calls an executor. Tested by AC-5-04, T5.1–T5.3, gate integrity, and the live smoke test.
2. **D-2 — out-of-scope and unknown intents are refused, never guessed.** Parser order: out-of-scope kinds are checked before sensitive verbs, so "Send a WhatsApp message" is refused as WhatsApp (out of MVP), not as a send. The listening pattern matches `track` alone.
3. **D-3 — missing facts become literal `[NEEDS INPUT: …]` placeholders, never invented figures.** Grounding check: 0 invented figures across the evaluation run.
4. **D-4 — brand voice applies only known mock tones** (`friendly`/`professional`/`playful` → that tone); anything else falls back to neutral with a note saying so. Agents 3/4 mock templates have no voice parameter, so brand voice cannot change their wording — recorded limitation.
5. **D-5 — recurring-question rule** (see §2): same classification-intent label ≥ minCount (default 3) across the latest classification of each inbox message and each comment; creates a content brief TASK only, never a draft publication. Labelled mock in code and evaluation output.
6. **D-6 — B-12 closed as advisory, not blocking** (see §2 and §6). A `block` verdict on an inbox reply does not refuse the approval request; the approver reviews the exact text and decides.
7. **D-7 — failure hardening: retry-once-then-escalate + dedupe + fail-closed.** Agent work retries once (`withRetryOnce`/`withRetryOnceSync`); a second failure produces a clear failed result + an escalation task, never a silent success or silent re-schedule (T5.6a: attempts 2, escalation task 1, suggestions unchanged 14→14). A forced publish failure leaves the post `failed`, attempts 1, job `failed`; a second `runDue` does not retry it (T5.6b). Idempotency replay adds `deduped: true` to the stored result. `forceFail` is a test-only hook.
8. **D-8 — `assistant_runs` is a module-owned table, not part of SCHEMA.** `src/agents/assistant.mjs` creates it lazily (`CREATE TABLE IF NOT EXISTS`) on the first assistant run. It is the only table outside `db.mjs` SCHEMA. Acceptable because it is write-only idempotency storage owned by the agent layer, but it is a divergence from the "schema lives in db.mjs" convention — recorded here.
9. **I-2 (coordinator integration fix) — pre-Phase-5 databases are rebuilt for the new CHECKs.** Stream 1's schema extensions assumed a fresh database; SQLite cannot ALTER a CHECK, so the pre-Phase-5 dev database (`app/data/meta-business-os.sqlite`, created in Phase 4) rejected `content_brief`/`review` tasks and `assistant`/`analysis` jobs with `CHECK constraint failed` — verified by the coordinator against a copy of the file. The fix (`src/db.mjs`: `rebuildTableForCheck`, called in `createDb` before the column migrations) renames the table, recreates it from SCHEMA, copies the intersecting columns, drops the legacy table, and re-runs SCHEMA to restore indexes — inside a transaction with foreign keys off (required: `ai_jobs` is referenced by `ai_suggestions`). Idempotent: fresh databases and databases already on the new schema are untouched; a second `createDb` on the same file is a no-op. Verified on an exact copy of the dev file (CHECKs rebuilt, indexes restored, `content_brief` + `review` tasks and `assistant` + `analysis` jobs insert with FKs enforced) and by a new regression test (`tests/db-migration.test.mjs`, built from SCHEMA with only the two CHECKs reverted — the exact pre-Phase-5 state). The stale NOTE in `createDb` was updated to match. The real dev file is still on the old CHECKs and will be rebuilt on its first Phase 5 start; it contains no rows (0 tenants/tasks/jobs).
10. **I-3 (coordinator integration fix) — the ask route forwards `contextRefs`.** Stream 1's `POST /api/assistant/ask` dropped `contextRefs`, so target-specific intents ("reply to this comment") returned `notDone` even though the agent layer (`runAssistantTask`) and the Orchestrator worker (`assistant_task`, via `intentContext`) already supported them. The fix forwards the body field, validated (plain object, known keys only: `postId`, `assetId`, `conversationId`, `commentId`, `sourceRef`, `from`, `to`, `ownerId`, `dueDate`; non-empty strings; unknown keys → 400). Regression test added (`tests/assistant-routes.test.mjs`: ask with `commentId` drafts a reply; without a target it says so plainly; bad refs are 400). The stale header comment in that test file ("the Stream 2 agent layer does not exist yet") and the Ask test's name were corrected in the same change.
11. **Correction to the Stream 2 report: `tests/evaluation.test.mjs` does not exist.** The T5.5 harness test lives in `tests/assistant.test.mjs` (line 775). The suite is 189 tests across 11 files (see §4); no coverage is missing — the file was named in the stream report but never created.
12. **Agent 1's `ai.draft_generated` audit entry now includes `suggestionId`** (1 line, `src/agents/content.mjs`, Stream 2). Audit completeness rose 25/30 → 30/30; no other behaviour changed.
13. **No-promise guard (same as Phases 3–4).** Analysis findings are descriptive summaries of stored data only; the harness records `noFuturePromise: true`.
14. **`/health` version stays `'phase1'`.** A Phase 1 test asserts it; the version field is a Phase 1 skeleton marker, not a release version.
15. **The `ask` fallback (agent layer absent) stays in the code but is unreachable in the built tree.** If `src/agents/assistant.mjs` were ever absent, `ask` would record a failed `ai_jobs` row and return a clear `notDone` (`agent_unavailable`) instead of inventing behaviour. Harmless resilience; the route test's fallback branch covers it only when the module is absent.

16. **I-4 (parent verification fix, 2026-11-10 ~08:55 CST) — demo step (14) was TZ-fragile.** The coordinator's demo run passed (24/24), but the parent's independent run in America/Chicago failed step (14): the assertion used `new Date(due_date).getDay() === 5` on the date-only string `2026-11-13` (Friday), which parses as UTC midnight = Thursday 18:00 CST, so `getDay()` returned 4. The product was correct — the task IS due Friday 2026-11-13 (the agent layer uses `getUTCDay()` throughout) — only the demo assertion was wrong. Fix (1 line, `scripts/demo-phase5.mjs`): `getDay()` → `getUTCDay()`. Re-verified: demo-phase5 PASSED 24/24 in America/Chicago AND under `TZ=UTC`; `npm test` still 189/189. The coordinator's "24/24" claim was environment-dependent; after this fix the demo is TZ-independent.
